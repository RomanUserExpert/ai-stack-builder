Phase 08 · Design tokens

The same look, a new architecture

Phase 8 of 12 · the course’s six steps and one of ours · 28–29 Oct 2026 · source of truth: tokens.css for the values, components/ for the look

Phase 07 dressed every screen from one flat file, and each of its variables knew its value but not whether that value was a colour or a role. This phase puts a layer of roles between the value and the component, splits the kit into tokens on two levels and one file per component, and moves every screen onto them — without a pixel moving. Then one theme proves it: light, made of semantic overrides alone, and not one component touched to get there.

START

Overview

A refactoring, not a redesign — and its test is that no screen moves.

What we saw

  • Our names were already roles. --ground, --problem, --on-lime said what a colour is for. What was missing was the level below — a palette of what a value is — so the phase added a floor under the names, not a ceiling over them.
  • Several variables carried more than one job. The lime was both the primary action and the current place’s mark; one grey was both secondary text and the Checked verdict. Same value today, different reasons — and the light slice already pulled two of them apart.
  • The literals hid inside the tokens, not the classes. Phase 07’s guard had kept every class clean, so the seven rgba() values sat in the shadows, the glass and the veil.
  • The second theme found what reading did not. Lime on white is 1.32:1, so a checked radio in light barely showed — a pair no measurement had covered.

What we decided

  • Two levels. A primitive says what a value is — hue plus a grade, 50, 100, 150…; a semantic token says what a colour is for, and names the uses it grew from.
  • A component reads colour only through a role, and geometry straight from a primitive. Geometry has no semantic level.
  • Two roles are two tokens, even when their value is the same today.
  • A theme overrides roles and nothing else. Dark is the product; light is the stress test, and whether it ships is the owner’s call.
  • No styling engine. Plain CSS, by hand — the two things this phase built.

STEP 01

The audit: every variable, and every job it does

Facts, not decisions — nothing was renamed, merged or fixed in this step.

tools/audit_tokens.py read every rule of the flat kit and every class on every dressed page, and for each of the kit’s 110 variables wrote down where it stands and the role it plays in each place. A role read off real uses is the only kind that may become a token: a semantic token with no addresses is thrown out.

STEP 02

Two levels: what a value is, and what it is for

One real chain, from the hex to the button that shows it.

Primitive--color-lime-100: #C6EF5A

What the value is: --color-, a hue and a grade — 50, 100, 150… from the lightest of that hue.

Semantic--action: var(--color-lime-100)

What the colour is for: the primary action. Its comment names the uses it grew from — 64 pages, 168 steps.

Component.button-primary{background: var(--action)}

The component knows the role and never the primitive. A theme changes the role; the button does not move.

Names in the namespaces everybody reads. As in Tailwind v4 and Primer: --color-*, --space-*, --radius-*, --font-*, --typescale-*, --size-*, --duration-*. The greys are neutral — Mica is the style’s name for them, not a hue. One scale per theme: --color-neutral-50 is the brightest text and --color-neutral-600 the dark ground; a value only light reads is --color-neutral-light-50…, because the quiet layers — 26 values, 1–2 % of lightness apart — do not fit one 50–950 grid of 19 steps. The washes, hovers and shadows are recipes over a role — color-mix() on --problem, --raised, --brand — so they follow the role into any theme.

And the refactor proves itself. tools/concept_tokens.py writes both token files from one source — phase 06’s flat one, unchanged to the byte, and this one — and refuses to finish unless every role resolves to the value phase 07 used, no hex appears that was not already signed, and every named geometry equals the calc() it replaced.

LAYER 1

Primitive: colour

What a colour is, and nothing about what it is for: --color-, a hue and a grade.

Each hue is a ladder, lightest first. --color-neutral-50 is the brightest text and --color-neutral-600 the dark ground. The greys are neutral — Mica is the style’s name for them, not a hue. There are two ladders, because the quiet layers — values 1–2 % of lightness apart — do not fit one 50–950 grid: 31 values the dark theme draws with, and 19 that only light reads, named --color-neutral-light-*. An alpha is a primitive too when it has no role of its own: the shadow’s black, the glass’s grey, the veil.

Each card says which roles read it, in which theme. A primitive no role reads would be dead weight, and the generator refuses one.

LAYER 1

Primitive: geometry

Space, radius, type, size, icons and motion — 74 primitives, and no semantic level above them.

A component reads geometry straight from here. A role says what a colour is for because a theme has to change it; nothing in a theme changes a radius, so a second name would only be a second place to drift. The names are the ones every system uses — Tailwind v4 and Primer: --space-4 is 16 px, --radius-md 10 px, --font-weight-semibold 600. The type styles are --typescale-*, Material’s word, because --text-* is already a colour role here.

Geometry is never a count of a primitive. calc(var(--space-12) * 3) was a dialog’s top; it is --offset-modal now, and guard 10 refuses the count coming back. The skeleton widths are the one kept exception: they are the length of the line they stand for.

LAYER 2

Semantic: colour

What a colour is for — 44 roles and 18 recipes, each a var() to a primitive or a mix of roles.

A theme overrides this level and nothing else. The two columns are the whole of the light theme’s work. Where light has no value of its own the role keeps the dark one and says so — 4 such gaps, signed in phase 09 or by the owner, never by a refactor.

STEP 03–04

Components, and every screen moved onto them

The flat kit split in two, and the old file deleted only once nothing differed.

tools/build_components.py sends every rule of the kit to its component’s file, in order — 27 files, imported by index.css in the kit’s order — and turns every phase-07 colour into the role its selector names. Because order between files can change which rule wins, it checks in a browser, on every page, that no reordering lets one rule override another.

Then the screens. Every page, the showcase and the shell now link two files, tokens.css and components/index.css. The pixel test against the goldens: 83 of 83 pages and 241 of 241 flow steps identical, the only differences two spots that were already flaky before the change, at 2/255. Only then was kit.css deleted; git keeps it.

STEP 05

The stress test: light

The course proves a light product with dark. Ours is dark, so light is the test — and the test was whether the architecture held.

[data-theme="light"] overrides 46 semantic tokens and nothing else — no primitive, no hex, no component. The values are not invented: they are phase 06’s signed light slice, role by role, each taking the light value of the variable it was split from. It needed zero component edits, which is the whole result: a theme that had needed one would have found a hole.

Beyond the sliceWhy
A lighter glassThe owner, on the preview: the glass is too dark. Light gets its own acrylic
A lighter sheet shadowThe owner: the shadow is too strong in light. The same offsets at 12 %
Deep Lime for a checked controlLime on white is 1.32:1, and a checked control needs 3:1. Deep Lime with a white tick reads 5.66:1

Four roles still draw dark in light — --sheet-edge and the Remove Red family — and they are listed in the theme block as gaps. Filling them is the owner’s word or phase 09’s, never a refactor’s. The contrast of 62 pairs is written into each theme block and measured on the file as written; every claim passes AA, and 1 — a tag’s outline — is recorded for information rather than claimed.

Ten guards, and they stop the build

  1. No literal in a component
  2. No style on a screen — no style=, no <style>
  3. Every class is a component’s, save a short named list
  4. Every variable is declared in tokens.css
  5. No colour primitive in a component new
  6. Two links, index.css imports every file, and kit.css never returns new
  7. One primary on any screen
  8. The words are the product’s: the showcase against microcopy.md
  9. Coverage: every page and flow step has a twin
  10. No geometry written as a count of a primitive new

Step 06 — conclusion

Every class of defect became a rule in kit_check.py, so none of them can come back unseen. A rule checked by a script is the only kind that survives the next change — judgement is what found them, and it is not what keeps them out.

STEP 07

The styling engine: none

The one question the course does not ask, and the specification had deferred to this phase since September.

Q6 was waiting for two built components, read against one criterion: tokens and two real themes first-class, and no utility classes pushed into components that are themselves the product’s value. Tailwind, CSS Modules and vanilla-extract were all live.

The owner answered before the comparison was made: there is no engine. The product is styled by plain CSS written by hand — the two things this phase built. The basis is stated plainly, because it is not a comparison: this work is homework, and its point is to understand how tokens, components and themes work, which an engine would do on our behalf. The criterion is met without one — custom properties carry both themes, a component is a CSS file with no utility class in it — and the guards already enforce it.
