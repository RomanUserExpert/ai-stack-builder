Phase 09 · Design system

A system with a rule of growth

Phase 9 of 12 · the course’s seven steps · 3 Nov 2026, closed · source of truth: design-system/, one package, one index.css

Phase 08 left the product with tokens and one file per component, and nothing that said how the system grows. This phase makes it a package with one entry point and gives it living documentation on that same stylesheet. It adds the four states in both themes, the compositions found on three screens or more, and one rule: new appears in the system first, on a screen second. Then it tests the rule twice, by building new screens from the system alone, and checks the system and the product against each other.

START

Overview

A folder with a new name is not a system. A system is a folder with a rule of growth, and a check that the rule holds.

What we saw

  • The showcase already existed and said nothing about when. The kit showed every component in every state, and never said when to take it or what to take instead.
  • No pressed state was drawn anywhere, and four roles had no light value of their own.
  • Building a new screen from the system alone found what reading had not. The tone of a neutral box was guessed from its first words, so a new sentence came out Problem rose.
  • The showcase online was unstyled. The folder’s address is served without its slash, so the page looked for its stylesheet one folder too high.

What we decided

  • One package at the root, design-system/, behind one index.css. It is the one named exception to one folder per phase.
  • The docs are the showcase, live on the product’s own stylesheet. kit.html is retired to a redirect.
  • States through roles, in both themes: pressed is one recipe per ground. Disabled is three roles and never an opacity. No state moves anything.
  • A pattern exists only if it can name three screens. The build counts them.
  • New appears in the system first, on a screen second. What the system lacks is written down as an order, never drawn on a screen.

STEP 01

One package, one entry point

Moved, not copied: tokens.css and components/ went into design-system/ unchanged to the byte.

Every screen, every flow step, the shell and the docs link one file, design-system/index.css. It imports the tokens, then the {{N_FILES}} component files. The pixel test came back identical on every page. The package sits at the root because phases 10–12 grow it and the app will consume it, so no phase number goes into its import paths (Q48, D1).

design-system/README.md ↗
STEP 02

Living documentation

A page per component: anatomy, variants and states, when to use it, a rule and an anti-rule.

The specimens are the screens’ own markup, cut from the real pages by the same function that built the kit, so the docs cannot disagree with the product. Each anatomy part is a selector, and the build finds it in its live specimen. The words come from tools/docs_content.py, and every specimen’s words are checked against microcopy.md. Why it looks like this is its own page, drawn from the concept and its references. Since the check the docs also hold every token and the five layouts.

STEP 03

Four states, two themes

Hover, active, focus-visible and disabled on every control, each beside rest, dark and light.

  • Pressed is nine recipes over a role, so it holds in both themes by construction. Each goes half a step past hover, in the direction hover went. Signed by the owner value by value (Q49).
  • Focus is the lime ring, measured at 3:1 or better on every ground in both themes.
  • Disabled is three roles and not-allowed. There is no opacity token, because opacity would dim the reason a disabled control points at (D3). In light its ground is #ECEDE6 (Q50).
  • Nothing moves. In both themes, the build checks in a browser that every state drawn differs from rest and changes nothing’s size.
STEP 04

Patterns found, not designed

Each pattern has a signature, and the build runs it over all 80 wireframe pages. It fails below three screens.

{{N_PATTERNS}} patterns: Browse head, Set with an item side panel, Configuring layout, Run report, Confirmation, and Dialog with a field. A screen counts once, and an overlay never counts. Seven compositions were looked at and refused, each with its count. Every pattern is a file with no style of its own.

STEP 05

The rule of growth

New appears in the system first, on a screen second, never the other way round.

  1. A value goes to tokens.css at its level, with a value in both themes, signed.
  2. A component goes to components/, with its docs page and its four states.
  3. A composition about to stand on its third screen goes to patterns/.
  4. What cannot enter yet goes to backlog.md. It is written down, not drawn.

The rule is written where the next session reads it: CLAUDE.md §18 and DESIGN.md. It is also in the code. Every guard that refuses a change names the section, and the token generator fails on a role with a value in one theme only.

STEP 06

New screens, from the system alone

Each screen answers a job no screen answered. Each has no style and no class of its own, and what it lacked became an order.

Usage of My library, for EJ-3, came first. The owner found it too familiar. Copies of code-style, for RJ-3 and H-J3, puts an item’s original beside its copy in each project, with the fields that differ. It found the defect the first one missed, and four more orders. Both are labelled as examples: whether the product has them is a register question.

STEP 07

The system and the product, checked together

The defect table first, then every row fixed, and every class of defect turned into a guard.

A new instrument, tools/system_check.py, compares in a browser every element of a docs specimen with the same element on every screen. /impeccable audit added its findings, and each was verified before it counted. The worst row was found while fixing: the showcase online loaded no stylesheet. Two classes came back clean: no state lives in one theme only, and no pattern has a style of its own.

Seventeen guards, and they stop the build

  1. No literal in a component
  2. No style on a screen
  3. Every class is a component’s
  4. Every variable is declared
  5. No colour primitive in a component
  6. One link, index.css
  7. One primary on any screen
  8. The words are the product’s
  9. Coverage: every page has a twin
  10. No geometry as a count
  11. A docs page per component new
  12. Patterns on three screens, no style new
  13. Examples: no style, labelled new
  14. A bare box is a Problem: tone is a class new
  15. Every class shown in the docs new
  16. Every token on the Tokens page new
  17. Docs and screens alike, in a browser new

Step 07 — conclusion

The drift was at the edges: variants the docs missed, layouts and tokens with no page, one tone guessed from words. None of it was a screen carrying a value of its own, because the earlier guards had held. The new ones close the edges.
